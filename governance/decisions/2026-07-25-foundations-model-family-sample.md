# Establish YOLO as the first model-family sample

## Context

`Foundations` 需要全面积累不同视觉模型，但直接批量建立模型目录会造成空架子、证据混用和长期维护负担。YOLO 又存在多作者分支、命名冲突、官方指标口径差异和复杂部署路径，适合检验目录是否真正可用。

## Decision

1. `Foundations` 以机制和任务为主知识层，以模型族为结构化索引层。
2. 每个一级目录维护独立的 `MAINTENANCE.md`，说明创建、补充、拆分/合并、删除和验收规则。
3. 模型族参考 YOLO 的八视图结构，但可按模型特点增删；偏离时必须在族入口说明。
4. 先只建立 YOLO 完整样板；核验目录粒度、证据质量和维护成本后，才允许扩展其他模型族。
5. YOLO 各分支分别绑定其作者论文、维护仓库和文档，不构造单一连续“官方谱系”。
6. 相关规则与样板形成少量、意图完整的提交，禁止按文件制造提交记录。

## Consequences

- 初期覆盖面较窄，但能在扩张前暴露维护问题。
- 官方资料缺失处会保留 `not disclosed` 或未知项，内容看起来不一定“完整”，但证据边界更可靠。
- 未来若 YOLO 八文件结构过重，应合并视图并在本决策后追加复盘，而不是机械复制到其他模型族。

## Revisit gate

至少完成一次实际查询、一次内容补充和一次部署问题回链后，评估：

- 查找一个版本的结构、训练、指标和部署信息需要多少跳转；
- 同一事实是否被重复维护；
- 更新一个版本是否需要修改过多文件；
- 官方、第三方和本人证据是否容易区分；
- 是否具备建立第二个模型族的必要性。

## 2026-07-25 复盘

三项实际动作已经完成：

1. 用 YOLO11、YOLO26、YOLOX 和 YOLO-World 做过版本与来源查询；
2. 做过一次较大范围的分支补充；
3. 已把 YOLO 部署页链接到量化精度诊断条目。

暴露出的主要问题是：补一次分支需要同时改 8 个页面，谱系和来源重复维护；`mechanisms/`、`tasks/` 也只有目录设计，没有真实内容。

本轮修正为：

- `variants.md` 是版本归属的唯一维护位置；
- `sources.md` 使用 Source ID 管原始资料；
- `architecture.md` 只讲机制变化；
- 建立一个目标检测任务页和一篇四机制说明；
- 新增普通分支通常只改 `variants.md` 和 `sources.md`，其他页面按实际变化补充。

目前结构已具备验收条件。

## Owner acceptance

2026-07-25，本人确认 YOLO 样板的目录分工和维护成本可以接受，可以作为后续模型族的建设参考。

该确认不表示所有 YOLO 分支、指标和部署结论均已独立复测；相关条目继续保持 `status: working` 和 `evidence_status: partial`。是否开始 MobileNet 或其他模型族，仍按实际需要单独决定。
